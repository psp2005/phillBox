공통 규칙

모든 API 에 적용
기본
Base URL/api (개발 http://localhost:3000/api)
앱 인증Authorization: Bearer <Supabase access token>
디바이스 인증X-Device-Key: <기기 API 키>
형식application/json
모든 시각UTC ISO 8601 "2026-08-23T23:00:00Z"
KST 변환은 화면이 한다
예외Medication.time 만 벽시계 값 "08:00"
모든 id문자열 (JS 숫자 정밀도 문제 회피)
전화번호숫자만 "01012345678" · 하이픈은 화면이 붙인다
응답 모양 규칙
  • 응답 최상위는 항상 객체로 감싼다
  • 하나만 돌려줄 때도 배열에 담는다 — { "devices": [ {...} ] }
    → 클라이언트 코드가 항상 같다. map() 이 어디서나 안전
  • "없음" 은 null 이 아니라 빈 배열 — { "medications": [] }
    → null 체크가 사라진다
  • 경로가 가리키는 자원 자체가 없으면 404 / 그 자원의 부속물이 없으면 200 + []
  • 자원은 경로, 거르는 조건은 쿼리스트링
오류 응답 — 표준이 없으므로 프로젝트에서 정한다
{
  "error": {
    "type":    "validation_error",
    "code":    "INVALID_CODE",
    "message": "등록코드가 일치하지 않습니다"
  }
}
message사용자가 읽는다. 화면 오류 띠에 그대로 출력
code프로그램 — 정확히 이 오류일 때만 분기
type프로그램 — 비슷한 오류를 묶어 같은 대응
type — 프론트가 어떻게 대응해야 하는가
auth_error로그인 화면으로 보낸다
permission_error목록으로 되돌리고 안내
validation_error그 화면에 머물며 입력을 고치게
state_error이미 처리됐거나 사라짐 → 화면을 새로 불러온다
상태 코드 (422 는 쓰지 않는다)
HTTPcode언제
400VALIDATION_ERROR필수값 누락, 형식 오류
400SERIAL_NOT_FOUND그런 일련번호 없음
400INVALID_CODE등록코드 불일치
400DOSE_NOT_DUE아직 오지 않은 복약 건
401UNAUTHORIZED토큰 없음·만료
401INVALID_DEVICE_KEY기기 API 키 틀림
403FORBIDDEN내 기기/내 알림이 아님
404DEVICE_NOT_FOUND경로의 기기 id 없음
404NOT_FOUND경로의 복약 건·알림 id 없음
409ALREADY_REGISTERED이미 등록된 기기
409ALREADY_TAKEN이미 복용 처리됨
401 과 403 — 401 은 "출입증을 안 보여줬다"(인증), 403 은 "출입증은 봤는데 이 층은 못 들어간다"(인가)

공통 객체 4개

어느 API 에서든 같은 필드 목록
Device
{
  "id":            "d3f1a2b4-9c8e-4f21-b7a3-0e5d6c1f8a92",
  "serial":        "PB-2026-0001",
  "nickname":      "할아버지 기기",
  "patient_phone": "01012345678",
  "timezone":      "Asia/Seoul"
}
registration_code · device_api_key 는 절대 내려주지 않는다.
등록코드가 새면 "기기를 만져본 사람만 안다" 는 전제가 깨지고, API 키가 새면 curl 로 taken 거짓 보고를 보낼 수 있다.
DB 컬럼 목록 ≠ API 응답 필드 목록.
  • patient_phone — 없으면 null. 있을 때만 화면 4 에 [전화 걸기]
  • timezone — 어느 화면도 안 쓴다. 서버가 "매일 08:00" 을 UTC 로 바꿀 때 쓰는 내부 계산용
Medication — 약 설정 = 시간표
{
  "id":        "31",
  "device_id": "d3f1a2b4-...",
  "name":      "혈압약",
  "dosage":    "1정",
  "time":      "08:00",
  "days":      [0, 1, 2, 3, 4, 5, 6]
}
★ time 은 UTC 가 아니다 — 시각 규칙의 유일한 예외
"매일 08:00" 은 순간이 아니라 규칙이라 UTC 로 바꿀 수 없다. UTC 로 바꾸려면 "어느 날의 08시" 인지가 있어야 하는데 매일 반복되는 값에는 날짜가 없다.

medications.time "08:00" + devices.timezone
  ↓ 서버가 그날의 복약 건을 만들 때 계산
doses.scheduled_at "2026-08-23T23:00:00Z"

시간표는 벽시계, 출석부는 UTC.
  • days — 0=일 ~ 6=토 (JS Date.getDay() 와 같은 번호)
  • 기기당 1줄이므로 배열에 0개 또는 1개뿐
Dose — 복약 건 = 출석부 한 줄
{
  "id":           "8821",
  "device_id":    "d3f1a2b4-...",
  "scheduled_at": "2026-08-23T23:00:00Z",
  "status":       "missed",
  "notified_at":  "2026-08-23T23:00:00Z",
  "dispensed_at": null,
  "taken_at":     null,
  "taken_source": null
}
statusscheduled · notified · dispensed · taken · missed
taken_sourceir · camera · manual · null
시각 4개를 항상 다 내려준다. missed 가 두 종류인 것을 화면이 구분해야 한다.
dispensed_at 이 비었는데 missed → ✕ 약을 안 꺼내셨어요
dispensed_at 이 있는데 missed → ⚠ 꺼내셨는데 아직 안 드셨어요
Notification
{
  "id":         "412",
  "device_id":  "d3f1a2b4-...",
  "dose_id":    "8821",
  "type":       "missed_not_dispensed",
  "message":    "약을 안 꺼내셨어요",
  "created_at": "2026-08-23T23:05:00Z",
  "read_at":    null
}
typemissed_not_dispensed (안 꺼냄)
missed_not_taken (꺼냈으나 미복용)
read_at안 읽었으면 null
message 는 서버가 type 으로부터 만든다. DB 에 저장하지 않는다.
· 저장 안 하는 이유 — 문구를 고치면 과거 알림까지 같이 바뀐다
· 서버가 만드는 이유 — 나중에 FCM 푸시도 같은 함수를 써야 목록과 푸시 문구가 어긋나지 않는다
기기 별명과 복약 건은 여기 안 담는다. devices · doses 배열을 따로 주고 화면이 id 로 짝을 맞춘다. 같은 기기 알림이 여러 개일 때 별명이 중복해서 실리는 것을 막고, 나중에 알림 목록에 기기 아이콘·전화 버튼을 넣어도 서버를 안 고친다.

왜 우리 서버를 거치지 않나
  • 회원가입·로그인·토큰 발급·만료 관리를 Supabase Auth 가 통째로 담당한다
  • 우리 서버(Express)는 발급된 토큰을 검증하기만 한다
// 로그인 (프론트에서 직접)
const { data, error } = await supabase.auth
  .signInWithPassword({ email, password })

// 이후 모든 API 호출에 이 토큰을 헤더로 실어 보낸다
fetch('/api/devices', {
  headers: { Authorization: `Bearer ${data.session.access_token}` }
})
서버가 토큰으로 하는 일
① Authorization 헤더에서 토큰을 꺼낸다
② 서명을 검증한다 (Supabase 가 발급한 것인지)
③ 토큰 안의 user_id 를 얻는다
④ 그 user_id 로 DB 를 조회한다

   SELECT d.* FROM devices d
   JOIN user_devices ud ON ud.device_id = d.id
   WHERE ud.user_id = '<토큰에서 얻은 값>'   ← "내 것" 이 걸러진다
클라이언트는 "누구의 데이터를 달라" 고 말하지 않는다. 말할 수 있게 두면 남의 user_id 를 적어 보내는 순간 뚫린다. 누구인지는 오직 토큰만이 말한다.
호텔에 비유하면 — 프런트에 "302호 열쇠 주세요" 라고 말하는 게 아니라, 카드키를 대면 기계가 알아서 그 사람 방만 열어주는 것.
화면이 받는 props (퍼블리싱 계약)
loading요청 중 (버튼 비활성 + 스피너)
error오류 문구 (없으면 null)
onLogin(values){ email, password }
onSignup(values){ email, password }
화면 검증은 형식까지만 — 빈칸, 이메일 모양, 6자 이상. "이미 가입된 이메일" 은 서버만 알 수 있으므로 error 로 받아 표시한다.

설계 요점
  • 배열을 나눠 주고 화면이 device_id 로 짝을 맞춘다. 카드 한 장에 devices + doses 두 테이블이 섞여 있다
  • today_doses — 기기 타임존 기준 오늘의 복약 건. 오늘이 복용 요일이 아니거나 약 미설정이면 그 기기의 줄이 없다
  • unread_count — 하단 탭 배지. 별도 API 없이 여기에 얹는다. 배지가 보이는 화면은 2·7 둘뿐이고, 폴링할 때 카드도 같이 갱신되는 이득이 있다
  • offset 페이지네이션인 이유 — 기기 목록은 보호자가 직접 등록할 때만 늘어나 순번이 밀릴 일이 없다. 정렬이 별명 가나다순이라 커서로 쓸 값(별명)이 중복 가능하고 한글 정렬 순서가 DB 설정에 따라 달라진다
  • 빈 상태 — 200 + 두 배열 모두 [], unread_count: 0 (404 아님)

등록 정보는 어디에 있나요?
일련번호와 등록코드는 기기 뒷면 스티커에 적혀 있습니다.
일련번호
PB-2026-0001
등록코드
A1B2C3
기기 별명 선택
할아버지 기기
등록하기
취소
열릴 때 서버를 부르지 않는다 — 빈 폼이다.
POST/api/user-devices [등록하기] 를 눌렀을 때
경로가 /api/devices 가 아닌 이유 — 이 API 가 만드는 것은 기기가 아니라 연결이다. 기기(PB-2026-0001)는 공장에서 이미 만들어져 DB 에 있고, 새로 생기는 것은 user_devices 의 한 줄이다. devices 테이블은 손대지 않는다.
나중에 "등록 해제" 를 만들 때도 DELETE /api/user-devices/:id 가 "연결을 끊는다" 로 정확히 읽힌다.
요청
POST /api/user-devices
Authorization: Bearer eyJhbGci...
Content-Type: application/json

{
  "serial":   "PB-2026-0001",
  "code":     "A1B2C3",
  "nickname": "할아버지 기기"
}
응답 201 Created
{
  "devices": [
    { "id": "d3f1a2b4-...", "serial": "PB-2026-0001",
      "nickname": "할아버지 기기",
      "patient_phone": null, "timezone": "Asia/Seoul" }
  ]
}
실패 응답
HTTPcodemessage (화면에 그대로 출력)
400VALIDATION_ERROR일련번호를 입력해 주세요
400VALIDATION_ERROR등록코드는 영문·숫자 6자리입니다
400SERIAL_NOT_FOUND해당 일련번호의 기기를 찾을 수 없습니다
400INVALID_CODE등록코드가 일치하지 않습니다
409ALREADY_REGISTERED이미 등록된 기기입니다
서버 처리
① devices 에서 serial 로 기기를 찾는다
   (대소문자·공백·하이픈을 무시하고 비교)
② code 가 맞는지 확인한다
③ user_devices 에 (user_id, device_id) 한 줄 추가
왜 등록코드가 필요한가 — 일련번호는 PB-2026-0001, 0002 … 순차적이다. 코드가 없다면 옆 번호를 찍어 남의 기기를 등록하고, 복약 기록을 보거나 복용 시간을 바꿔버릴 수 있다.
일련번호는 공개돼야 쓸모 있는 값(AS 문의 시 불러줌)이고, 등록코드는 기기를 실제로 가진 사람만 아는 값이다.
서버는 클라이언트를 믿지 않는다. 화면이 trim().toUpperCase() 를 하지만 서버도 반드시 해야 한다 — curl 로 직접 보낼 수 있다.
화면의 정리는 사용자 편의, 서버의 정리는 필수.
등록 성공 후 — 화면 2 로 이동한 뒤 GET /api/devices 를 다시 호출한다. 가나다순 정렬 + 페이지네이션 때문에 프론트가 새 기기를 끼워 넣을 위치를 판단할 수 없다.

★ scheduled_at 으로 어느 복약 건인지 특정한다 — 가장 놓치기 쉬웠던 부분
디바이스는 dose_id(8821)를 말할 수 없다. 그 번호는 DB 가 만든 것이고 스케줄 응답에 들어 있지도 않다. 병원 접수번호와 같다 — 환자는 자기 번호를 모르지만 "3시 예약이요" 라고 말할 수 있다.
그래서 파이가 계산할 수 있는 값으로 지목한다. device_id 는 API 키가 말해준다.
WHERE device_id = <키에서 알아낸 기기> AND scheduled_at = <요청 값>
초안 { status, occurred_at, taken_source? } 은 셋 다 "어느 건인지" 를 말해주지 않았다. 구현 단계에서 발견했으면 디바이스 파이썬 코드까지 고쳐야 했다.
occurred_at 이 따로 있는 이유 — 08:03 에 꺼냈는데 와이파이가 끊겨 11:00 에 보고가 도착할 수 있다. "받은 시각"(11:00)을 적으면 기록이 틀린다. 서버는 받은 시각을 쓰지 않는다. 오프라인 큐를 붙여 밀린 기록을 한꺼번에 보내도 시각이 안 어긋난다.
  • 복약 건이 아직 없으면 서버가 그때 만든다 — 미리 만들어두는 크론이 필요 없다
  • status=taken 이면 taken_source 필수 (ir/camera) · 실패 — 401 INVALID_DEVICE_KEY / 400 VALIDATION_ERROR

모든 API 공통 · 이 프로젝트의 심장
요청한 보호자가 user_devices 에 그 기기와 연결돼 있는지 매번 확인한다.
확인 없이 device_id 만 믿으면, 남의 id 를 넣어 보내는 것만으로 다른 사람의 복약 기록이 노출된다.
뚫리는 시나리오
보호자가 자기 앱에서 개발자도구를 열어

  GET /api/devices/<남의기기UUID>/doses?from=...&to=...
  Authorization: Bearer <자기 토큰>

를 보내면?

  확인 없이 처리하면
  → 남의 할아버지 복약 기록이 그대로 온다
  → 화면 5 를 부르면 복용 시간을 바꿔버릴 수도 있다
원칙
누구인지는 토큰이 말하고, 무엇을 요청했는지는 URL 이 말한다.
서버는 매번 "이 토큰의 주인이 이 기기와 연결돼 있나" 를 user_devices 에서 확인한다. 
SELECT 1 FROM user_devices
WHERE user_id   = '<토큰에서 얻은 값>'
  AND device_id = '<URL 의 :id>';

// 없으면 403 FORBIDDEN
테이블 구조가 이걸 가능하게 한다
devices                    user_devices
┌──────────────────┐      ┌────────────────────────┐
│ id     d3f1      │◀─────│ user_id 아들  device d3f1│
│ serial PB-2026-. │◀─────│ user_id 딸    device d3f1│
└──────────────────┘      └────────────────────────┘
                             두 줄이 있으면 둘이 같은 기기를 본다
devices.id 는 기기를 가리키지 사람을 가리키지 않는다. 아들이 보든 딸이 보든 같은 값이고, 누가 요청했는지는 토큰이 말한다.
사람별 구분은 user_devices.user_id 가 한다.
:id 가 기기가 아닌 API
API확인할 것
POST /api/doses/:id/taken 그 복약 건의 device_id 를 꺼내서 그 기기가 내 것인지
doses → devices → user_devices 로 거슬러 올라간다
POST /api/notifications/:id/read 그 알림의 user_id 가 나인지
notifications 에 user_id 가 직접 있어 한 단계로 끝난다
403 vs 404
403선택. 디버깅이 쉽다 — "없는 건가 / 권한이 없는 건가" 가 구분된다
404"그런 게 존재하는지" 조차 안 알려줘 더 안전하다는 견해도 있다
이 프로젝트는 등록코드라는 자물쇠가 따로 있어 존재 여부 노출의 위험이 낮다고 보고 403 으로 통일한다.
디바이스도 같다
API 키에 묶인 기기의 데이터만 읽고 쓸 수 있다.
POST /api/device/events 의 scheduled_at 으로 복약 건을 찾을 때도 "그 키의 기기" 로 범위를 좁혀서 찾아야 한다.
